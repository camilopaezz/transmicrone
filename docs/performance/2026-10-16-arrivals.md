# Arrival request concurrency, October 16, 2026

The station client now launches every selected service variant concurrently. It
still waits for every variant, filters and deduplicates the responses, and
preserves the previous complete board if any variant fails. Stop-summary requests
are unchanged. No timeout or automatic refresh setting changed.

## Experiment

- Baseline is the exact `BodegaFeedClient` source at commit
  `4d1f20442f4c38c0745ab7e7195f8372041150db`, generated under a different class name
  only for this experiment. The baseline keeps its coroutine semaphore of two.
- Both clients run inside the same Android instrumentation process on
  `Dev_Pixel_8_API_36`, Android 16, x86_64. They share one production-configured
  OkHttp client, HTTP/2 connections, parser, installation UUID, and live feed
  credentials. This is a live Android-networking measurement, not a mocked-delay
  simulation or a measurement on a physical Xiaomi.
- Workloads come from the packaged Ricaurte NQS station catalog, `TM0069`.
  S43/S48 produce four requests: S43 IDs 13277, 13278, 13279 and S48 ID 13267.
  Adding B12 IDs 12874, 11876 and J23 IDs 11712, 12070 produces eight requests.
  These are plausible selections, not an export of a user's saved board.
- Two experiment windows each contain six paired rounds per workload, alternating
  AB and BA order. Each window has a complete initial
  round of both workloads and both modes as warm-up, excluded from summaries.
- Device streaming was stopped during warm-up, before any measured round. No
  concurrent Android builds or other Android test suites ran during measured
  rounds. The emulator uses the workstation network, not a cellular radio.
- Starts are at least 25 seconds apart, matching the app's polling interval.
  Runs never overlap. A run longer than 25 seconds finishes before the next
  begins. The benchmark does not reproduce the UI timer's skip-to-next-tick
  behavior after an overrun.
- Connect timeout is 10 seconds, read timeout 15 seconds, whole-call timeout
  25 seconds, and automatic connection retries are disabled, as in production.
- Monotonic timing covers the full `fetchArrivals` operation through filtering
  and deduplication. Per-call timing uses OkHttp `callStart` through `callEnd` or
  `callFailed`, including connection establishment and body consumption.
  `start_offset_ms` measures when a call starts relative to its board. For the
  baseline, it includes waiting for a semaphore permit. It also includes small
  coroutine scheduling and request construction costs, so it is not a pure
  semaphore-wait measurement.
- Each observation retains HTTP status, byte count, protocol, request identity,
  maximum concurrent calls, final board outcome, arrival count, and known source
  report ages. Headers, installation identifiers, and response bodies are omitted.
- Complete-result latency includes both populated and successfully empty boards.
  Failures are reported separately and never treated as successful speedups.
  Every individual pair is retained so changes in feed content remain visible.

## Collection and retained evidence

The first window finished successfully, but Gradle's connected-test runner
uninstalled the application afterwards, deleting the on-device raw file. All 28
whole-board totals, outcomes, modes, and workload sizes were recovered from its
instrumentation log and retained as `2026-10-16-arrivals-first-run-totals.jsonl`.
Per-call data for that window is unavailable and is not reconstructed.

The collection fix runs instrumentation directly after in-place APK updates,
retains the app's data, clears the previous benchmark cache before starting, and
publishes only after confirmed instrumentation success. It validates every
round/mode/workload combination and its call count before atomically saving
output. Host experiments use isolated Gradle execution and a fresh staging file,
so a skipped test cannot reuse old observations. Full JSON observations are also written to the instrumentation log
as a backup. The second window repeats the same schedule and workloads, with
complete per-call data. The first window remains part of the report.

Each window uses a stable installation UUID shared by both modes. The UUID changed
between windows because the first runner removed the installation. Compare modes
within each window; pooled figures are descriptive across those two windows.

## Reproduce

Configure the ignored feed settings described in [feed.md](../feed.md). Run from
the repository root with a connected Android emulator and JDK/SDK configured:

```sh
python3 scripts/benchmark-arrivals.py --device emulator-5554 \
  --output /tmp/arrivals-android.jsonl
python3 scripts/summarize-arrivals-benchmark.py /tmp/arrivals-android.jsonl
```

The launcher generates benchmark-only source from the baseline commit and cleans
it up afterwards. Device mode uses that app installation's persisted UUID.
Omit `--device` to run the same experiment on the host JVM with the PC tooling's
persistent UUID. Host and Android results must be reported separately.

## Interpretation limits

Two windows of six pairs per workload can expose queueing and large latency
changes, but cannot establish long-term reliability, mobile-radio behavior, or tail
percentiles. The live server and arrivals change between requests. Interleaving
balances order and time effects; it cannot hold the remote server constant.
Shared warm connections describe ongoing polling. Cold-start performance and
rendering are outside this measurement. Removing the explicit semaphore leaves
normal coroutine-dispatcher, socket, HTTP/2, and server resource limits in place.

## Results

Across both windows: 48 measured refreshes, 8 excluded warm-ups, and 336 live
variant calls including warm-up. Each mode has 12 measured refreshes per workload.
Every measured non-completion was a timeout.

| Requests per board | Two at a time: complete median | Uncapped: complete median | Complete capped / uncapped | Timeouts capped / uncapped |
| --- | --- | --- | --- | --- |
| 4 | 4.43 s | 4.26 s | 10/12 / 8/12 | 2 / 4 |
| 8 | 13.58 s | 6.12 s | 6/12 / 10/12 | 6 / 2 |

Medians include successful empty results and exclude failures. There was one
empty result, on a capped four-request board in the repeat. All other completed
measured boards contained arrivals. Medians describe only refreshes that
completed, so the completion counts must be read alongside them.

Eight-request boards benefited in this sample: the uncapped median among complete
refreshes was about 55% lower and 10/12 completed versus 6/12 capped. Four-request
medians were nearly equal, while uncapped had four timeouts versus two capped.
These observations do not establish that removing the cap caused the timeout
difference or that either failure rate will persist.

The feed changed substantially between windows:

| Window | Requests | Capped complete median and count | Uncapped complete median and count |
| --- | --- | --- | --- |
| 1 | 4 | 6.34 s, 6/6 | 4.37 s, 4/6 |
| 1 | 8 | 17.35 s, 5/6 | 6.29 s, 5/6 |
| 2 | 4 | 1.80 s, 4/6 | 1.54 s, 4/6 |
| 2 | 8 | 1.48 s, 1/6 | 0.57 s, 5/6 |

The repeat's capped eight-request median comes from just one complete refresh.
It must not be read as typical eight-request performance.

In the repeat, the median last-request start offset fell from 318 ms to 2.7 ms
for four requests, and from 2714 ms to 7.4 ms for eight. Recorded peak concurrent
calls were exactly 2 capped, versus 4 or 8 uncapped. Every expected call was
accounted for in all 28 detailed observations. The repeat's measured arrival
observations with known source times were 41 to 101 seconds old.

The first warm-up had one capped and two uncapped timeouts. The repeat warm-up
had one capped timeout. Warm-ups are retained in the raw files and excluded only
from the measured summaries.

## Validation

- The four-request barrier regression failed on the original client, then passed
  after removing the semaphore. The server holds all responses until every
  selected variant reaches it, so queued requests cannot silently pass the test.
- 114 Android JVM tests passed; the opt-in live benchmark was skipped in the
  ordinary suite. Both live Android instrumentation experiments passed separately.
- All 18 Python tests passed after review, including checks that failed
  instrumentation and incomplete traces cannot publish old or partial output.
  The analysis tests verify that fast failures and warm-up
  cannot lower successful medians, transport failures cannot count as complete
  empty boards, and different experiment windows cannot be paired together.
- `:app:lintDebug` and `:app:assembleDebug` passed with `-PmockFeed=false`.

```sh
cd android
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug -PmockFeed=false
cd ..
python3 -m unittest discover -s tests -v
```
